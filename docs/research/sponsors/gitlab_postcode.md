# GitLab features for the post-code lifecycle (October 2026)

Research for Alex Velazquez's Life After Code entry (GitLab Transcend Hackathon, Path A). Written 2026-10-06.

How to read this file:

- docs.gitlab.com and about.gitlab.com are blocked from this research environment (see [Blocked](#blocked)). Every documentation fact below was read from the documentation source in the [gitlab-org/gitlab](https://gitlab.com/gitlab-org/gitlab) repository at commit `4f2a68658f43ab122b2edaea1d1bde3db7612ecf` (the `master` branch on 2026-10-06). Each row gives two links: `docs` is the page a browser shows on docs.gitlab.com, `src` is the raw Markdown I read.
- "Tier" is the `Tier:` badge GitLab prints at the top of the page or of the section.
- "Free on GitLab.com?" means a GitLab.com Free namespace can use it without buying anything. "Partial" means only part of it works on Free.
- Anything I could not confirm is marked (unverified). Stage names in the feature table are my mapping onto GitLab's nine lifecycle stages (see the next section), not a GitLab label.

## Summary

- GitLab's lifecycle has nine stages: Plan, Create, Verify, Package, Secure, Release, Configure, Monitor, Govern. Seven are post-code (Verify to Govern); Create is partly post-code because code review sits there. The live stages page could not be read, so the feature lists under each stage come from GitLab's product data, not the page.
- Free on GitLab.com covers a full loop: pipelines (400 compute minutes a month), schedules, trigger tokens, environments, review apps, deployment tracking, releases, feature flags, the alert HTTP endpoint, incidents with timeline events, integrated error tracking, GitLab Observability (experiment, free for all tiers), Service Desk, webhooks, REST and GraphQL, the GitLab MCP server (beta).
- Paid gates that matter: protected environments and deployment approvals (Premium); on-call schedules, escalation policies and paging (Premium); auto-creating incidents from alerts, Auto Rollback, Status Page, vulnerability report, dependency scanning, DAST, security policies and all agentic security flows (Ultimate). Duo Agent Platform needs Premium or Ultimate, or GitLab Credits bought on Free.
- The hackathon group `gitlab-ai-hackathon` is at least Premium (its license-gated `epicsEnabled` field is `true`) and is very likely Ultimate (it runs a pipeline execution policy and assigns a custom member role, both Ultimate features). Inferred, not confirmed.
- Best hook points: Duo Agent Platform flow triggers (pipeline, merge request, work item events), project webhooks (pipeline, job, deployment, work item, release, feature flag, vulnerability), the alert HTTP endpoint, pipeline trigger tokens (a webhook can start a pipeline and pass its payload), and comments with quick actions (`/severity`, `/timeline`, `/page`, `/run_pipeline`).

## Lifecycle stages (GitLab's official list)

The official page is https://about.gitlab.com/stages-devops-lifecycle/. It is blocked here, and its source is not public (see [Moved or broken links](#moved-or-broken-links)), so I could not read it directly.

The nine stage names, exactly as GitLab writes them in its reference project for this hackathon (built by a listed judge per [docs/RULES.md](../../RULES.md); README last edited 2026-10-05; it links to the stages page):

> "Every stage of the GitLab DevSecOps lifecycle: **Plan** · **Create** · **Verify** · **Package** · **Secure** · **Release** · **Configure** · **Monitor** · **Govern**"

Source: [hello-world-showcase README](https://gitlab.com/gitlab-org/developer-relations/contributor-success/hello-world-showcase/-/blob/main/README.md). The Devpost page lists the same nine in lowercase ("plan · create · verify · package · secure · release · configure · monitor · govern"), per a search excerpt recorded in [docs/RULES.md](../../RULES.md). The website repository that served the page until July 2025 lists these sub-pages as migrated routes: configure, continuous-delivery, create, enablement, govern, monitor, package, plan, release, secure, verify ([route.ignore.js](https://gitlab.com/gitlab-com/marketing/digital-experience/buyer-experience/-/blob/main/route.ignore.js)).

Post-code marking follows GitLab's own wording for this hackathon: automate "any part of the software development lifecycle after the code is written, from review and testing through to deployment, monitoring, and incident response" (TranscendHackathonPage.vue, quoted in [docs/RULES.md](../../RULES.md)).

Features under each stage: the live page could not be read (unverified). The right column lists GitLab's own product categories marked `marketing: true` in [data/categories.yml](https://gitlab.com/gitlab-com/www-gitlab-com/-/blob/master/data/categories.yml) (updated 2026-09-21), placed under the nine stages by me.

| Stage | Post-code? | GitLab product categories (marketing: true), my placement |
|---|---|---|
| Plan | No | Team Planning, Planning Views, Portfolio Management, Wiki, Pages, Service Desk |
| Create | Partly (code review) | Source Code Management, Workspaces, Code Review Workflow, Code Suggestions, GitLab CLI |
| Verify | Yes | Continuous Integration (CI), Code Testing and Coverage, Merge Trains, Review Apps |
| Package | Yes | Package Registry, Container Registry, Helm Chart Registry, Virtual Registry, Artifact Registry, Dependency Firewall |
| Secure | Yes | SAST, Secret Detection, Code Quality, Software Composition Analysis, Container Scanning, DAST, API Security, Fuzz Testing, Vulnerability Management, Dependency Management, Secrets Management |
| Release | Yes | Continuous Delivery, Release Orchestration, Feature Flags, Environment Management, Deployment Management |
| Configure | Yes | Auto DevOps, Infrastructure as Code |
| Monitor | Yes | Incident Management, On-call Schedule Management, Observability |
| Govern | Yes | Security Policy Management, Compliance Management, Audit Events, Release Evidence, Software Supply Chain Security, Security Testing Configuration, Security Asset Inventories, Security Testing Integrations |
| (cross-stage analytics) | Yes | DORA Metrics, Value Stream Management, DevOps Reports, Custom Dashboards Foundation |

Note: GitLab's internal product hierarchy no longer uses the names Secure, Release, Configure, Monitor or Govern. [data/stages.yml](https://gitlab.com/gitlab-com/www-gitlab-com/-/blob/master/data/stages.yml) (updated 2026-10-05) has stages such as Verify, Package, Deploy, Application Security Testing, Security Factory, Security Governance, Security Platform, Analytics, AI Coding and Agent Foundations. For example, feature flags, environments and releases belong to the internal stage "Deploy", and incident management and observability to "Analytics". For judging, use the nine marketing names above.

## Agent hook points

Ranked by how useful they are for a post-code agent, with the tier each needs.

### Places to listen

1. **Duo Agent Platform flow triggers** (Premium or Ultimate). No server needed; the flow runs as a service account in CI. The best fits for post-code work are "Pipeline events" (Failed, Passed), "Merge request: Approved" or "Created", and "Work item: Created" or "Status changed" (with a status filter, 19.4). Caveat: "All trigger event types require a human user to perform the triggering action. A non-human user such as a bot user, service account user, or another flow, cannot activate a trigger." So an incident that a bot or an alert creates will probably not start a "Work item: Created" flow (my inference). [docs](https://docs.gitlab.com/user/duo_agent_platform/triggers/#actions-that-dont-initiate-a-trigger) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/duo_agent_platform/triggers/_index.md))
2. **Project webhooks** (Free; Maintainer). Most useful events: Pipeline Hook, Job Hook (has `build_failure_reason`), Deployment Hook (running, success, failed, canceled, blocked; approved and rejected on Premium), Issue Hook for work item events (incidents arrive as `object_kind: work_item` with `severity`; Service Desk tickets as `object_kind: issue`), Note Hook (comments), Release Hook, Feature Flag Hook, Vulnerability Hook (needs Ultimate scanners), Duo Flow Callback (experiment). The receiver must answer within 10 seconds and should queue work, and should verify the `webhook-signature` header. [docs](https://docs.gitlab.com/user/project/integrations/webhook_events/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/integrations/webhook_events.md)) [docs](https://docs.gitlab.com/user/project/integrations/webhooks/#webhook-receiver-requirements) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/integrations/webhooks.md))
3. **Alert HTTP endpoint** (Free for one endpoint). Any monitor, a script, or a canary check can `POST` JSON and GitLab creates or groups an alert; `end_time` resolves it; incidents can close themselves on recovery. Auto-creating the incident is Ultimate; on Free, the agent creates the incident itself through the Issues API. There is no webhook for alerts, so poll GraphQL `alertManagementAlerts` or have the sender also notify the agent. [docs](https://docs.gitlab.com/operations/incident_management/integrations/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/incident_management/integrations.md)) [docs](https://docs.gitlab.com/operations/incident_management/manage_incidents/#automatically-close-incidents-via-recovery-alerts) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/incident_management/manage_incidents.md))
4. **Pipeline trigger URL as a webhook target** (Free). A webhook can call `/projects/:id/ref/:ref/trigger/pipeline?token=...`; the job reads the event from `$TRIGGER_PAYLOAD`. This turns any GitLab event into a CI job that runs the agent, with no server of your own. GitLab documents it for push and tag events; other event types are (unverified). [docs](https://docs.gitlab.com/ci/triggers/#use-a-webhook) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/ci/triggers/_index.md))
5. **Scheduled pipelines** (Free). Periodic sweeps: stale environments, flaky tests, dependency checks, error-trend summaries. Free limits: 24 runs per schedule per day, 10 schedules per project. [docs](https://docs.gitlab.com/ci/pipelines/schedules/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/ci/pipelines/schedules.md)) [docs](https://docs.gitlab.com/user/gitlab_com/#cicd) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/gitlab_com/_index.md))
6. **GitLab Observability queries** (Free, experiment). After a deploy, an agent can query error rate and latency through the SigNoz API or the Observability MCP server and decide whether to continue, flip a flag, or ask a human to roll back. [docs](https://docs.gitlab.com/operations/observability/api_access/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/observability/api_access.md)) [docs](https://docs.gitlab.com/operations/observability/mcp_server/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/observability/mcp_server.md))
7. **Service Desk** (Free). Customer emails become tickets that fire Issue events; an agent can triage them and link them to incidents or releases. [docs](https://docs.gitlab.com/user/project/service_desk/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/service_desk/_index.md))

### Gaps to design around

- No webhook for alerts or for error tracking events; poll GraphQL or route the signal through your own receiver.
- Flow triggers ignore actions taken by bots, service accounts and other flows.
- `CI_JOB_TOKEN` cannot create issues or comments; on GitLab.com Free there are no project access tokens, so use a service account token or a personal token stored as a masked, protected CI/CD variable. [docs](https://docs.gitlab.com/ci/jobs/ci_job_token/#job-token-access) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/ci/jobs/ci_job_token.md)) [docs](https://docs.gitlab.com/user/project/settings/project_access_tokens/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/settings/project_access_tokens.md))
- On GitLab.com, rate limits are moving to per-plan limits; the 19.4 release notes say Free accounts and anonymous requests change first, from 2026-10-19, which is inside the hackathon window. Authenticate every agent request. [19.4 what's new](https://gitlab.com/gitlab-org/gitlab/-/blob/master/data/whats_new/202609170001_19_04.yml) [docs](https://docs.gitlab.com/user/gitlab_com/rate_limits/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/gitlab_com/rate_limits.md))

## What GitLab would be proud to see

These points come from what GitLab itself says it wants; my own reading is marked as such.

1. **Monitoring and incident response, not just a smoke test.** GitLab's hackathon guide says: "Monitoring and incident response are part of life after code, so your subgroup can have its own observability instance." ([ShowcaseDetails.md](https://gitlab.com/gitlab-org/developer-relations/contributor-success/contributors-gitlab-com/-/blob/main/contributors/app/javascript/pages/transcend-hackathon-page/ShowcaseDetails.md)). GitLab describes Observability as a way to "Correlate code changes with production issues" and to "See recent deployments, code changes, and the developers involved in one place" ([docs](https://docs.gitlab.com/operations/observability/observability/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/observability/observability.md))). A loop from telemetry to alert to incident to fix to release uses exactly that story.
2. **The newest agent plumbing, used for real.** Flow triggers on pipeline, merge request and work item events (18.9 to 19.4), the Flows API with webhook callbacks (19.4), the GitLab MCP server with pipeline tools (19.4) and the Observability MCP server (19.3) are all recent. Using them shows the judges the parts GitLab just shipped.
3. **Breadth across the nine stages with real GitLab objects.** One run that touches a pipeline (Verify), a package or image (Package), a scan (Secure), an environment, flag and release (Release), an IaC or Kubernetes step (Configure), an alert and incident (Monitor) and an approval or audit trail (Govern) maps directly onto the "Most Stages Covered" prize.
4. **A person in control where it matters.** Deployment approvals, protected environments, manual jobs and tool governance are GitLab's own control points. Using them, instead of letting the agent deploy on its own, fits the project rules in [AGENTS.md](../../../AGENTS.md).
5. **Bringing quiet features back to life (my reading).** Incident management and Service Desk carry the note "This feature is not under active development, but community contributions are welcome." ([docs](https://docs.gitlab.com/operations/incident_management/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/incident_management/_index.md)) [docs](https://docs.gitlab.com/user/project/service_desk/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/service_desk/_index.md))). An agent that makes them useful again through the APIs is a creative angle.
6. **Works on Free (my reading).** A core loop built on Free features (alert endpoint, incidents, timeline, feature flags, environments, releases, Observability, webhooks) can be copied by any GitLab.com user; paid features can be added as optional layers.
7. **Avoid deprecated paths.** Use `glab` instead of `release-cli`; GraphQL instead of the REST Vulnerabilities API; plan for the Unleash Proxy end of life on 2026-11-26 (GitLab says Unleash Edge does not work with GitLab feature flags); do not build on compliance pipelines (removal in 20.0). [docs](https://docs.gitlab.com/user/project/releases/release_cli/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/user/project/releases/release_cli.md)) [docs](https://docs.gitlab.com/api/vulnerabilities/) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/api/vulnerabilities.md)) [docs](https://docs.gitlab.com/operations/feature_flags/#maximum-supported-clients-in-application-nodes) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/operations/feature_flags.md)) [docs](https://docs.gitlab.com/update/deprecations/#compliance-pipelines) ([src](https://gitlab.com/gitlab-org/gitlab/-/raw/master/doc/update/deprecations.md))
