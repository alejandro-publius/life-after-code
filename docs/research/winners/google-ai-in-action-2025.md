## 1. Pipeline Doctor (GitLab Track, 1st or 2nd). Deep-dived: no

- **GitLab's summary:** "Pipeline Doctor uses AI for root cause analysis of CI/CD failures to improve pipeline reliability." ([GitLab blog](https://about.gitlab.com/blog/ai-in-action-hackathon-celebrating-the-gitlab-innovations/), search excerpt)
- **What it does:** a Spring Boot (Java 17) service on Cloud Run that listens for GitLab pipeline webhooks. When a pipeline fails, it takes the first failed job and runs these steps ([WebhookController.java](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/src/main/java/com/pipelinedoctor/controller/WebhookController.java), [GitLabPipelineService.java](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/src/main/java/com/pipelinedoctor/service/GitLabPipelineService.java)):
  1. Pulls the job log through the GitLab Jobs API and asks Gemini 2.0 Flash to explain the root cause in a fixed markdown template.
  2. Embeds the log with `gemini-embedding-exp-03-07` (3,072 dimensions) and runs MongoDB Atlas `$vectorSearch` for the 3 most similar past failures. Gemini turns them into a table headed "Similar Job Failures Found via AI Vector Search".
  3. Posts both as a merge request comment if the pipeline belongs to an MR. Otherwise it emails the commit author through SendGrid, skipping "noreply" addresses.
  4. Asks Gemini for a corrected `.gitlab-ci.yml`, creates branch `ai-ci-fix-job-<id>`, commits the file ("AI: Fix .gitlab-ci.yml") and opens an MR labelled `ai-generated` with a Gemini-written explanation ([GitlabCiFixService.java](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/src/main/java/com/pipelinedoctor/service/GitlabCiFixService.java)).
  5. Saves the failure and its embedding to MongoDB, so later searches can find it.
- **GitLab features and depth: moderate to deep.** It uses pipeline webhooks plus the Jobs, MR notes, branches, commits and merge requests APIs. It also ships a reusable CI/CD component (`templates/pipeline-doctor.yml`) that is **published in the GitLab CI/CD Catalog** (versions v1.0.0 on 2025-06-14 and v1.0.2 on 2025-06-15, verification level "UNVERIFIED", 0 stars; checked with the gitlab.com GraphQL `ciCatalogResource` query). The repo's topics are "AI Generated Suggestions", "AI Pipeline Analysis" and "GitLab CICD Components" ([project API](https://gitlab.com/api/v4/projects/69755411)). The component itself is small: one job that `curl`s a JSON body to the webhook URL ([template](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/templates/pipeline-doctor.yml)). That fits the brief's "functional components submitted to the GitLab CI/CD Catalog" line.
- **CI config:** [`.gitlab-ci.yml`](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/.gitlab-ci.yml) has build, deploy and release stages. It builds with Gradle, builds and pushes a Docker image to Artifact Registry, deploys with `gcloud run deploy` and five Secret Manager secrets, and runs `release-cli` on tags to publish the catalog version. One caution: the `docker-auth` job decodes the service-account key to `key.json` and keeps it as a job artifact (`expose_as: "Docker Config and Key"`, `expire_in: 15m`).
- **Google Cloud tools and depth: moderate.** It uses Gemini 2.0 Flash and a Gemini embedding model, both through the Gemini API with an API key (not Vertex AI). It also uses Cloud Run, Artifact Registry, Secret Manager and a dedicated service account ([deploy_to_gcp.sh](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/scripts/deploy_to_gcp.sh)). It is unusual in using **both partners**: MongoDB Atlas Vector Search ([bootstrap_mongo.sh](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/scripts/bootstrap_mongo.sh)) as well as GitLab.
- **Autonomy: it acts alone up to the MR, and a human approves the merge.** No one is asked before it comments, sends email, creates a branch, commits or opens an MR. The only gate is that a person has to merge the MR. It skips a job if an MR for that job already exists.
- **Code-quality notes (my reading of the source):** the fix step is called as `suggestAndCreateFix(projectId, jobId, jobLogs, parsedExplanation, "main")`. That puts the AI's explanation in the parameter meant for the current `.gitlab-ci.yml`, and it hard-codes `main` as the target branch ([GitLabPipelineService.java](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/src/main/java/com/pipelinedoctor/service/GitLabPipelineService.java)). So Gemini writes the "fixed" file without seeing the real one. The repo shows the result. It has 102 branches, 97 of them `ai-ci-fix...` branches made by the tool's bot account ([branches API](https://gitlab.com/api/v4/projects/69755411/repository/branches?per_page=100)). In the one bot commit I opened, the 61-line pipeline was replaced by a 15-line file with a single `step` stage ([commit 594657a9](https://gitlab.com/vanichitkara18/pipeline-doctor/-/commit/594657a978d5a475b8dab6e603169c7b17c40336)). There is one test, a context-load check ([PipelineDoctorTests.java](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/src/test/java/com/pipelinedoctor/PipelineDoctorTests.java)).
- **Demo style and video:** not found. YouTube and the Devpost page are blocked, and a YouTube-only search found nothing. The ~97 bot branches, all from June 1, 2025 in the commits I listed, suggest the author fired the webhook many times against this repo while building or recording the demo (my guess).
- **Human or emotional story:** developer pain, with no named person. README: "Developers who are frustrated with cryptic job failures." and "Pipeline Doctor is not just a monitor - it's an intelligent assistant for your CI/CD failures. It learns, compares, explains, and fixes - so you don't have to." ([README](https://gitlab.com/vanichitkara18/pipeline-doctor/-/blob/main/README.md))
- **Live URL:** none. The README only gives an example (`https://pipeline-doctor-xyz.a.run.app`), since each user deploys their own instance.
- **Team and build history:** one human committer, Vani Chitkara (two emails, one a GitHub noreply address) ([contributors API](https://gitlab.com/api/v4/projects/69755411/repository/contributors)). The project was created May 11, 2025. `main` has 41 commits from "Initial Commit" (May 11) to June 15, 2025, mostly titled "Add changes for project submission readiness" ([commits](https://gitlab.com/vanichitkara18/pipeline-doctor/-/commits/main)). The MR and pipeline lists are not public (API 403). License: MIT.
- **README structure:** badges (MIT, GitLab CI, Java 17, Gemini) → a one-paragraph pitch → Features (4 items) → Project Structure (tree) → Tech Stack → "How to Use This as a CI/CD Component" in 3 steps (deploy to Cloud Run with a Secret Manager table, bootstrap MongoDB Atlas, `include: component`) → How It Works (numbered) → Best Practices (securing the webhook, secrets, rate limits, monitoring) → Development / Testing → Ideal For → "Why Pipeline Doctor?" → Contributing → License. It has no screenshots, no diagram, no video link and no Devpost link.
- **Why it most likely won (my reading):** it hits the GitLab brief almost word for word: a real, published CI/CD Catalog component built on Google Cloud. It tackles a problem every judge has had (a red pipeline with a cryptic log) and closes the loop from failure to explanation, similar past failures, and a fix MR. It also uses the other partner's product (MongoDB vector search) in a sensible way. The weak fix logic would not show in a 3-minute video.

## Patterns

1. **All three GitLab winners work after the commit, in the pipeline.** One explains and fixes failed pipelines, one makes release and rollback decisions, one runs agents as CI jobs. None is a coding assistant. This is the same post-code space as "Life After Code".
2. **The brief rewarded GitLab-native packaging.** Devpost asked for "functional components submitted to the GitLab CI/CD Catalog". The likely top winner actually published one (v1.0.0 and v1.0.2). The 3rd-place winner showed a catalog badge and a `ci-catalog/` folder without publishing.
3. **The Google side was light.** Both readable winners call Gemini 2.0 Flash, mostly through an API key, and deploy one service to Cloud Run with Secret Manager. Neither uses ADK or Vertex AI Agent Builder in its main path. Judges seem to have weighed the GitLab integration and the idea more than Google Cloud depth (my inference).
